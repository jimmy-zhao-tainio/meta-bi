# MetaPipeline Load Concern Triage

## Purpose

This note reads [`../meta-load/META-LOAD.md`](../meta-load/META-LOAD.md) and
[`../meta-load/META-LOAD-DESIGN-QUESTIONS.md`](../meta-load/META-LOAD-DESIGN-QUESTIONS.md) against the current
`MetaPipeline` slice.

The goal is not to pull every ETL concern into `MetaPipeline`.
The goal is to decide whether each concern family is:

- already owned by `MetaPipeline`
- a real `MetaPipeline` gap
- better owned by `MetaTransformScript` / `MetaTransformBinding`
- better generated by a future `MetaPipelinePattern`
- better owned by `MetaOrchestration`
- better owned by sanctioned business, Data Vault, data warehouse, data quality, or deployment models
- intentionally unsupported for the current slice

## Current Stance

`MetaPipeline` is the executable local pipeline unit.

It should:

- execute a declared serial task chain
- run one bound `TransformScript` per transform-backed task
- materialize SELECT-kind row streams through the modeled `InsertRows` target write
- execute SQL-shaped mutation scripts as `MetaTransformScript` statements
- resolve connection references from environment variables
- supply runtime execution context values
- report and optionally persist run/task evidence
- fail honestly

It should not become:

- a scheduler
- a dependency freshness engine
- a checkpoint/watermark brain
- a high-level SCD/delta/Data Vault/DW pattern executor
- a SQL mini-DML abstraction layer
- a source connector universe before those carriers are actually modeled

## Ownership Map

### MetaTransformScript and MetaTransformBinding

Own SQL-shaped semantics and structural binding.

This includes:

- `SELECT`, `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE`, and `MERGE` statement syntax
- SQL predicates, joins, CTEs, functions, `MERGE` clauses, and other statement structure
- source and target object references discovered from modeled SQL
- source/output/target rowset shape discovery
- source/target structural validation against sanctioned schema workspaces
- sanctioned data type compatibility through a selected `MetaDataTypeConversion` workspace

Load concerns that are expressed as SQL should usually land here or in generated SQL from
patterns, not as pipeline task primitives.

### MetaPipelinePattern

The likely role is user-facing load templates that generate modeled artifacts.

It should generate, not execute:

- `MetaTransformScript` scripts
- `MetaTransformBinding` rows
- `MetaPipeline` serial task chains
- expected target-write or validation task declarations when those are part of the pattern

Candidate pattern families:

- full refresh
- append
- insert-only
- merge/upsert
- delete-detecting load
- Data Vault raw load
- Business Vault derived load
- data warehouse dimension/fact load
- SCD load shapes once the data warehouse model can say what that means

Patterns are the right place for reusable SQL templates and load recipes.
They are not the right place for runtime scheduling state.

### MetaPipeline

Owns execution mechanics for one local pipeline unit.

This includes:

- modeled pipeline/task graph validation for the supported serial shape
- task ordering inside one pipeline
- row-stream buffering and `InsertRows` movement
- the `InsertRows` runtime target data type system selection
- transform execution against SQL Server connections
- SQL Server session context values for task/run metadata
- connection-reference resolution and safe missing-secret diagnostics
- task status, failure stage, failure message, row/batch metrics
- optional operational DB evidence persistence
- explicit operational DB bootstrap/prune commands

Future concern families that plausibly belong in `MetaPipeline` because the executor must honor
them directly:

- modeled pipeline parameters / control values passed to scripts
- richer operational evidence such as source artifact/window values

These are not all required immediately, but they are the main places where
[`../meta-load/META-LOAD.md`](../meta-load/META-LOAD.md)
still points back at `MetaPipeline` rather than away from it.

### MetaPipeline Operational DB

Owns runtime evidence only.

It can store:

- pipeline runs
- task runs
- logs
- failures
- metrics
- audit ids
- retention/prune evidence

It should not store:

- modeled product truth
- connection strings
- scheduling policy
- dependency freshness
- checkpoints
- watermark semantics
- replay decisions
- orchestration state

If future watermarks or source-artifact identities are used by a pattern, the operational DB may
record the values as evidence, but it should not become the semantic owner of how they advance.

### MetaOrchestration

Owns decisions above one local pipeline unit.

This includes:

- schedules and triggers
- cross-pipeline dependencies
- dependency freshness
- fan-out/fan-in across pipelines
- tenant/partition execution planning
- retries and backoff policy
- queues, priority, and resource class
- approval gates
- environment promotion and run eligibility
- recurring runs, backfills, and catch-up plans

`MetaPipeline` may expose metadata and evidence that orchestration can use.
It should not decide those policies itself.

### Sanctioned Business, Data Vault, Data Warehouse, and Analytics Models

Own business and target semantics.

This includes:

- business keys and grain
- conformed dimensions and facts
- SCD semantics
- source-system identity meaning
- survivorship rules
- Data Vault hubs, links, satellites, effectivity, and platform columns
- data warehouse dimension/fact contracts
- reference-resolution semantics
- analytics model semantics

`MetaPipeline` can run tasks that implement these semantics.
It should not invent those semantics.

### MetaDataQuality

Owns explicit quality and contract rules when they are not merely structural binding checks.

This includes:

- duplicate detection
- missing reference checks
- value/domain checks
- thresholds and severities once modeled
- warning/error/reject decisions once modeled
- reconciliation and control-total checks

`MetaPipeline` may eventually execute declared validation tasks and record their evidence.
The rules themselves should remain modeled outside the plain executor.

### Deployment, Environment, Security, and Operations

Own concerns that are not data movement semantics:

- schema deployment and migrations
- permissions and secrets management
- credential rotation
- SQL Agent or external scheduler jobs
- production retention jobs around `prune-pipeline-db`
- environment promotion
- sensitive data governance

`MetaPipeline` should keep not logging secrets and should fail clearly when required runtime
prerequisites are missing.

## Concern-Family Triage

| `META-LOAD` family | Primary owner | MetaPipeline impact |
| --- | --- | --- |
| Source acquisition | Stage 1 database source in `MetaPipeline`; broader source families later need modeled carriers/connectors | Current database row-stream execution is in scope. Files/API/messages/object store are not yet supported. |
| Change detection | `MetaPipelinePattern`, `MetaTransformScript`, DW/DV models | Do not add generic change-detection state to the executor. |
| Temporal semantics | Business/DV/DW models plus generated scripts | Pipeline supplies task/run timestamps only. |
| Target write semantics | `MetaTransformScript` for SQL mutations; `MetaPipeline` for `InsertRows` row movement and target runtime type-system selection; patterns for recipes | Avoid mini-DML primitives. Use `MetaDataTypeConversion` as the explicit type conversion policy workspace. |
| Data quality/contracts | `MetaTransformBinding` structural checks and `MetaDataQuality` rules | Pipeline can execute/report declared checks later. |
| Idempotency/replay/recovery | Patterns, self-recovering scripts, orchestration | Pipeline records failures and should stay deterministic; no generic checkpoint brain. |
| Orchestration/dependency | `MetaOrchestration` except local serial task order | Pipeline owns only internal task order and validation. |
| Logging/observability/audit | `MetaPipeline` operational DB | This is a real pipeline responsibility; evidence may need more fields over time. |
| Performance/scale | Split: SQL/platform tuning, orchestration parallelism, pipeline buffering/bulk copy | Pipeline owns batch/buffer/write mechanics, not global workload planning. |
| Platform/environment | Runtime env refs in `MetaPipeline`; deployment/ops elsewhere | Keep connection strings out of metadata. |
| Security/governance | External ops/deploy/governance plus safe pipeline diagnostics | Pipeline must avoid secret leakage and keep destructive behavior explicit SQL. |
| Business loading | Business/DV/DW models and generated patterns | Pipeline executes the resulting tasks only. |
| Reference resolution/keying | DW/DV/business models and generated SQL/patterns | Pipeline should not become a row-by-row lookup engine by default. |
| Custom behavior/extensibility | `MetaPipelinePattern` and explicit transform scripts first | Avoid opaque runtime plugins until a modeled extension contract exists. |

## Remaining MetaPipeline Confidence Gaps

Before calling `MetaPipeline` done for the current layer, decide these explicitly:

1. **Pipeline parameters / control values**
   - Current docs mention parameters/control values, but the stage 1 executor mostly uses fixed CLI/workspace values and SQL Server session context.
   - If templates need runtime values, those values need a modeled path into execution and evidence.

2. **Source artifact/window evidence**
   - The operational DB records runs, task runs, logs, failures, metrics, audit ids, timeout settings, row counts, and workspace fingerprints.
   - It does not yet record source artifact/window values because those values are not modeled pipeline inputs yet.
   - These can be evidence-only later without making the operational DB own replay or watermark semantics.

Closed in the current slice:

- **Execution connection role**
  - `TransformExecutionTask` now owns an explicit `ExecutionConnectionReference`.
  - `meta-pipeline add-step` and `execute-sqlserver` require `--execution-connection-env`.
  - SELECT-kind tasks add a separate `--target-connection-env` only when materializing through `InsertRows`.
  - There is no implicit source/default connection and no CLI `--...-ref` surface.

- **Transaction boundary**
  - `MetaPipeline` does not provide `BeginTransaction` / `EndTransaction` task primitives.
  - The sanctioned current policy is per task/statement execution. SQL-shaped atomicity belongs inside the transform script or generated SQL pattern.
  - Operational DB evidence is outside data transactions so failures and partial progress remain visible.

- **Failure policy**
  - The sanctioned current policy is `StopOnFirstFailure`.
  - Serial execution stops at the first failed transform/write step and records remaining modeled steps as skipped.
  - Continue-on-error is intentionally unsupported until there is a concrete modeled policy need.

- **Operational row-count evidence**
  - SELECT-to-`InsertRows` records row and batch counts.
  - SQL mutation tasks record SQL Server rows affected where SQL Server reports a value.
  - Statements that do not report affected rows, such as some DDL-like operations, remain `0` row-count evidence rather than inferred counts.

- **Declared validation tasks**
  - No special validation-task family is needed in the current slice.
  - Validation/check behavior can be represented as user-authored transform scripts when it is SQL-shaped.
  - `MetaDataQuality` remains the owner of data-quality semantics if richer rule execution is modeled later.

- **Timeout/cancellation mechanics**
  - `TransformExecutionTask.TimeoutSeconds` is an optional modeled timeout.
  - `meta-pipeline add-step` and direct `execute-sqlserver` accept `--timeout-seconds`.
  - Omitted timeout means no SQL command timeout; explicit values are applied to SQL commands and SQL Server bulk copy.
  - Timeout evidence is recorded on `TaskRun`, not as a run-wide setting.

- **Operational fingerprint evidence**
  - The operational DB records SHA-256 workspace fingerprints in `RunFingerprint`.
  - Run-level fingerprints cover the pipeline, transform, and binding workspaces used for execution.
  - Task-level fingerprints attach the transform workspace to each transform script id and the binding workspace to each transform binding id.
  - Explicit data-type conversion workspaces are fingerprinted for affected target-write tasks.
  - Source schema workspace fingerprints are not recorded at execution because the schema workspaces are binding-time inputs, not current execution inputs; the binding workspace fingerprint is the executable contract evidence for now.

## Working Conclusion

`MetaPipeline` is not finished as a confidence story until the gaps above are either implemented,
explicitly deferred, or documented as intentionally unsupported.

But the bulk of [`../meta-load/META-LOAD.md`](../meta-load/META-LOAD.md) does not belong inside `MetaPipeline`.
Most concern families should be demoted to:

- SQL scripts and bindings
- generated pattern artifacts
- orchestration policy
- sanctioned business/DV/DW models
- data-quality models
- external operations/deployment tooling

The next `MetaPipeline` work should therefore be a bounded confidence pass, not a broad ETL
platform expansion.
